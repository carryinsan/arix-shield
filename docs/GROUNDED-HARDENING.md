# Grounded hardening extensions (v1.4.2)

These are opt-in controls layered onto the existing ArixShield integration. They do not turn source code into a network scrubbing service, a universal SQL interception layer, a Raft consensus implementation, or a host firewall.

## 1. Gateway TLS and edge pre-shedding

`edge/gateway.mjs` uses the normal Node TLS handshake. With `EDGE_ALLOWED_SNI_HOSTS` set, its `SNICallback` rejects unapproved SNI names; a post-handshake guard also closes connections without an allowed SNI name before HTTP request handling. Optional client-certificate authentication uses `requestCert`, a configured CA, and `rejectUnauthorized`. The gateway never reads a custom TCP preamble and does not alter TLS ClientHello bytes.

When active request/connection pressure crosses `EDGE_SHED_THRESHOLD`, the gateway contracts `headersTimeout` and `keepAliveTimeout` with hysteresis. It is a per-process admission/timeout measure, not global DDoS scrubbing. Deploy behind a provider that protects the upstream link, and firewall the origin to gateway egress addresses while requiring the existing origin proof.

The root `proxy.js` is an optional framework-independent Vercel Routing Middleware entrypoint configured through `vercel.json` (`proxy.entrypoint`). It uses the pinned first-party `@vercel/functions` `next()` helper to continue normal routing. It accepts standard Web `Request` objects and does not import or require Next.js.  `ARIX_EDGE_PROOF_REQUIRED=true` requires an HMAC ticket in `X-Arix-Edge-Ticket` or the `arix_edge_clearance` cookie. Tickets are generated by `createEdgeClearanceTicket()` in `api/_lib/edge-clearance.js`, signed from the already configured `ARIX_MASTER_SECRET`, audience/path/method-bound and valid for at most five minutes. The middleware rejects invalid traffic before the route handler is invoked. It is not a complete bot challenge or a guarantee of zero edge compute. The `x-arix-edge-verified` marker response header is informational; origin authorization must continue to use the existing Ed25519 gateway proof.

## 2. Database tenant scoping and response receipts

Use `withTenantTransaction(client, context, fn, options)` from `api/_lib/db-guard.js` inside the request context established by the SDK. PostgreSQL executes `BEGIN`, transaction-local `set_config('arix.tenant_id', ...)` / `set_config('arix.user_id', ...)`, callback queries and `COMMIT`; exceptions roll back. PostgreSQL RLS policies must explicitly consume those settings and be tested for every tenant table. `verifyDatabaseRlsActive(pgClient, tables)` checks `relrowsecurity`, `relforcerowsecurity`, and rejects superuser / `BYPASSRLS` runtime roles.

Prisma is supported through explicit `$transaction` use with a declared provider. MySQL receives transaction-session variables; that is not PostgreSQL RLS and is only useful with reviewed policies/views/triggers that consume them. SQLite has no native RLS and requires a caller-supplied connection-local enforcement adapter. The helper does not intercept unwrapped clients, native addons, arbitrary SQL sockets, or other processes.

Successful wrapped transactions and protected Prisma operations add a request-scoped HMAC receipt held in module-private `WeakMap` state. With `requireScopedDataReceipt: true`, the Node and Next.js SDKs block a 200 JSON response if the active request has no matching receipt. The Node adapter buffers up to 4 MiB of JSON output before release; larger protected JSON responses are rejected rather than leaked. This receipt proves that a reviewed wrapper ran in the request context; it does not prove that an arbitrary query's SQL semantics are tenant-safe or that the developer used the wrapper for every data access.

`scripts/check.mjs` also includes a dependency-free database-import boundary tripwire. It is not a complete ECMAScript AST/data-flow proof and cannot stop runtime dynamic loading or code outside the scanned tree.

## 3. Optional WAL-backed state service; Upstash remains primary

`state/replicated-state-server.mjs` is a separate, optional HTTP/HTTPS state service. A primary assigns monotonically increasing sequence numbers, appends hash-chained prepare/commit records to a disk WAL, fsyncs them, and requires a majority of the configured primary-plus-replica nodes to acknowledge prepare and commit before reporting success. Replicas authenticate peer messages using HMAC-SHA256 derived from the existing `ARIX_MASTER_SECRET`. REST access reuses `UPSTASH_REDIS_REST_TOKEN`; no new API key is introduced.

This is a single-primary, quorum-replicated WAL service—not Raft, not a leader-election protocol, and not automatic failover. Operators must prevent split-brain, fence the old primary before promotion, monitor sequence/hash agreement, and restore/rebuild stale replicas. A crash with unresolved prepare/commit/finalization records places a node read-only for operator reconciliation. The WAL contains stored Redis keys and values in plaintext and needs host-level disk/backup protection; its hash chain is not an externally anchored tamper-proof log, and the current implementation has no compaction.

Its Redis-compatible command subset is deliberately bounded. It does **not** implement the Lua `EVAL` scripts used by the current ArixShield Upstash client, so it is not a drop-in replacement for the application's full distributed state contract. Do not point the production ArixShield `UPSTASH_REDIS_REST_URL` at this service without implementing and independently testing all required Lua semantics. The existing Upstash primary remains required and unchanged.

`UPSTASH_REDIS_FALLBACK_URL` / `TOKEN` are opt-in and are used only after the primary circuit is open and `UPSTASH_REDIS_FALLBACK_SHARED_STATE=true` is explicitly set. That flag is an operator assertion, not cryptographic proof of replication. Use only with provider topology that guarantees a shared, synchronously replicated keyspace. An unrelated secondary Redis instance is unsafe for replay guards, sessions and rate limits.

The alert outbox is stored in the existing Redis primary under `arix:outbox:alerts:<projectId>`, uses a bounded queue and processing list, and is drained by `/api/cron/audit-anchor`. A short project lease prevents overlapping cron drains. Delivery is at-least-once: a crash after receiver acceptance but before acknowledgement can duplicate a webhook. Receivers should deduplicate on `outboxId`. Dead-letter retention is bounded.

## 4. Opt-in Node egress guard and host firewall generation

`installSafeGlobalAgents()` replaces Node `http.globalAgent` / `https.globalAgent` for clients that honor those agents. Its lookup hook validates all DNS answers for non-allowlisted public HTTPS targets and rejects non-HTTPS destinations unless explicitly allowlisted. `installSafeGlobalFetch()` explicitly wraps `globalThis.fetch` and routes non-allowlisted origins through `arixSafeFetch`. Both return `restore()` handles and are opt-in; call them at application boot and retain the handles for controlled shutdown.

These hooks do not intercept raw `net.Socket`, TLS clients that bypass the global agents, native addons, subprocesses, every Undici dispatcher configuration, or traffic from other processes. The kernel layer is generated separately: `node scripts/generate-egress-firewall.mjs --uid 65532` emits an nftables fragment that an operator must review and apply. The generator does not install rules, configure routes, or replace the provider firewall. Test the selected UID and required infrastructure allowlist before rollout; an overly broad allowlist weakens the policy.

## 5. Container configuration and boot attestation

`Dockerfile.hardened`, `docker-compose.hardened.yml`, `docker-compose.mtls.yml`, `docker-compose.state.yml`, and `seccomp-profile.json` provide a non-root (`65532:65532`), read-only, no-new-privileges, all-capabilities-dropped deployment profile with resource limits and an explicit syscall allowlist. The base compose file does not require optional state-service TLS files; add `docker-compose.state.yml` only when deliberately starting the separate state profile, and add `docker-compose.mtls.yml` only when supplying a trusted client CA bundle. Review and test the seccomp profile on the target kernel/architecture before production. The profile may need compatibility adjustments for the exact Node base image; a blocked syscall can prevent startup or a runtime operation.

`verifyDeploymentHardening()` observes the live process UID and, on Linux, `/proc/self/status` `NoNewPrivs` / `CapEff`. It does not activate seccomp, nftables or filesystem restrictions. With `ARIX_REQUIRE_HARDENED_RUNTIME=true`, the gateway startup check fails closed if required controls are absent. PostgreSQL checks require the caller to pass a live SQL executor and explicit table list; the library never silently executes `ALTER TABLE` or creates policies. `api/health.js` reports an unavailable RLS executor as an attestation issue rather than pretending it verified database state.

`scripts/build.mjs` writes `docs/BUILD-PROVENANCE.json` after a clean, non-empty Node 22 test run. It binds the exact source-manifest root, Node version, build timestamp and test pass/total counts using HMAC-SHA256 from the existing `ARIX_MASTER_SECRET`. This is local HMAC build provenance, not an independently witnessed SLSA attestation. Production checks require a valid signature; a distributable ZIP without the owner's secret cannot contain a valid production signature. Run `npm run build` in the owner's trusted CI with the production secret configured before release.

## Validation boundary

Local syntax/import checks, unit tests, test fixtures, source hashes and HMAC verification are reproducible repository evidence. They do not establish live TLS certificate validity, correct origin firewall rules, actual mTLS peer enrollment, Redis replication consistency, database policy correctness on a customer database, kernel enforcement after deployment, resistance to volumetric DDoS, or OWASP ASVS 5.0.0 Level 3 certification. These require deployment-specific tests and independent assessment.
