# ArixShield v3 implementation status

**Package version:** 1.4.2

**Assessment boundary:** source files and deterministic local tests only. No customer application, production database, customer ingress, cloud account, key custodian, independent SOC, or production network was available.

This matrix distinguishes a repository primitive from an end-to-end production control. A module being present does not mean every route or customer deployment uses it. **Partial** means useful code exists but one or more integration, persistence, infrastructure, coverage, or independent-verification requirements remain. No ASVS certification or zero-vulnerability claim is made.

The submitted brief says “18 domains” but defines only Domains 1–17. No Domain 18 has been inferred.

## Integration requirements for new primitives

- **Password filter:** the embedded default is only 89 curated seed examples. Compile a vetted local breach list with `npm run compile:breach-filter -- input.txt output.json`; keep provenance, licensing and update cadence for that list. The output is a 16-bit XOR filter, not a Binary Fuse filter. The default structure uses approximately 2.6 bytes per entry at its configured load factor, with an approximately 1/65,536 fingerprint false-positive probability. False positives are possible; a negative result does not establish that a password has never appeared in a breach.
- **Recovery codes:** show plaintext codes once, store only `{salt,digest}` records, and implement `consumeDigest` using an atomic database/Redis compare-and-delete. Couple successful recovery to MFA/session re-enrollment and revocation in the application transaction.
- **Origin lock:** all API routes now opt out of provider body parsing and the shared Vercel adapter verifies proof before route execution whenever `ARIX_ORIGIN_PUBLIC_KEY` or `ARIX_ORIGIN_LOCK_REQUIRED=true` is configured. Keep the private key only at the edge, publish the matching public key to the origin, set origin lock required, provide shared Redis for nonce replay protection, and enforce ingress allowlisting/mTLS at the network layer. The gateway does not provide upstream volumetric DDoS scrubbing. Do not trust a client-provided `x-arix-client-ip` without a valid proof.
- **Database policy:** `compile-policy` takes an OpenAPI document and a separate exact `METHOD /path` policy map. It writes a default-deny compiled artifact; it does not alter handlers. The RLS generator supports straightforward PostgreSQL `CREATE TABLE` definitions with a `tenant_id` column; manually inspect and test generated migrations, table owners, superuser roles and views.
- **KMS:** user/project Redis records now use envelope encryption on `setJson`/`getJson`; legacy records migrate on first read. Production requires the existing 32+ byte `ARIX_MASTER_SECRET`, or all referenced versioned KEKs in `ARIX_CUSTOMER_RECORD_KEKS_JSON`. Keep previous KEKs during backup migration; validate key custody, restore and rotation before retiring a version.
- **Audit ratchet:** implement `store.read()` and an atomic `store.commit(expectedVersion, nextState, record)` transaction. Do not emulate this with separate writes. Keep key storage and retention under independent custody.
- **SOC and DR:** inject durable transactional storage; local Maps are development/test fallbacks. Ensure a rollback token maps to a real reversible action in the application before enabling containment.

## Physical and compliance boundaries

A host's L3/L4 DDoS scrubbing, origin firewall, TLS/mTLS edge binding, kernel egress controls, container policy, database-native RLS, and regional quorum are properties of the deployed network/host/database. Adding JavaScript source cannot activate them. A 500 Gbps flood cannot be absorbed by an application function after saturating a smaller physical circuit.

The local test suite is deterministic regression evidence. It does not establish absence of vulnerabilities, universal false-positive/negative rates, volumetric DDoS resistance, customer route coverage, key custody, RPO/RTO or ASVS compliance. OWASP ASVS 5.0.0 Level 3 verification requires a requirement-by-requirement evidence map against the complete customer application and deployed environment plus appropriate independent assessment.
