# ArixShield v1.4.1 hardening notes

## Implemented in this increment

1. **MFA recovery lifecycle:** first TOTP confirmation or first passkey registration creates eight independent 128-bit recovery codes. Only salted SHA-256 digests are stored in the user record; plaintext codes are returned once. `recover-mfa` requires the account email, password and one recovery code, consumes the matched digest through Redis `SET NX`, clears TOTP/passkey factors and credential mappings, revokes existing sessions and issues a fresh session.
2. **Session-family replay response:** sessions carry a random family identifier and are indexed in Redis. Password and MFA changes rotate the current session; the old token receives a `SET NX` spent marker. Reuse of a spent cookie triggers revocation of the replacement session family. Session-family indexes are bounded; an over-limit condition throws rather than silently truncating the revocation set.
3. **Password denylist root checking:** the existing 89-entry curated seed and 16-bit three-part XOR filter remain unchanged in algorithm and corpus size. The policy now tests exact bounded roots after trailing numeric/year and punctuation suffixes. This is weak-password pattern screening, not proof of a verified breached corpus.
4. **ZIP integrity:** archive inspection validates central/local filename, flags, compression method and size/CRC metadata. Data descriptors are checked when bit 3 is set. Entry extraction checks uncompressed byte count and IEEE CRC-32; Office archive inspection expands bounded entries and therefore exercises those checks.
5. **Database constructor tripwire:** `scripts/check.mjs` rejects several common direct DB-client construction forms inside `api/` and `sdk/`. This is intentionally described as a lexical tripwire; it is not an AST or data-flow proof and does not wrap third-party clients.
6. **PostgreSQL RLS diagnostics:** generated policies use `ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY`, and emitted SQL includes an application-role diagnostic for superuser / `BYPASSRLS` attributes. `FORCE` does not constrain PostgreSQL superusers or `BYPASSRLS` roles; deployment must use a non-superuser, non-BYPASSRLS application role.


7. **Redis configuration downgrade prevention:** Upstash REST URLs are normalized only when they are credential-free HTTPS origin/root URLs on the default secure port; malformed or partially-present URL/token configuration now throws instead of silently selecting the process-local preview store. Configuration diagnostics remain non-throwing and distinguish invalid configuration from an intentionally unconfigured local preview.
8. **Outbound fetch deadline and redirect isolation:** `arixSafeFetch` applies one absolute deadline across DNS resolution, TLS, response headers and body transfer; it rejects non-global destinations, limits request/response sizes, pins the resolved public address, restricts ports, and rejects cross-origin redirects. Same-origin method rewriting follows the 301/302/303 rules; credentials and arbitrary caller headers are never carried to another origin because that redirect is not followed.
9. **Complete API-tree integrity coverage and production preflight:** Runtime integrity verification checks every `api/**/*.js` and `api/**/*.mjs` route/shared module against the API-bundled manifest, rejects API symlinks, and detects missing, extra or drifted API source files. Vercel API functions include `api/**/*`; the runtime manifest is mirrored inside that tree and is checked byte-for-byte against the canonical documentation manifest by the static gate. The production build gate validates Node 22, independent master/cron secrets, HTTPS Redis REST configuration, and an RSA clearance private JWK of at least 3072 bits before signing the manifest and running all deterministic tests.

## Intentionally not implemented from the supplied blueprint

- **Synthetic dictionary permutations are not called a breach corpus.** Generating 50,000 derived strings from names, years and suffixes creates synthetic weak-password patterns, not 50,000 independently verified compromised passwords. A trustworthy breached-password corpus needs documented provenance, licensing/usage rights, update process and data validation.
- **The filter is not renamed Binary Fuse.** The implementation is a three-part XOR filter. A Binary Fuse filter needs its own reviewed algorithm, construction/peeling proof, compatibility format, and measured space/false-positive behavior. Rebranding the existing structure would be false.
- **A compressed-byte Kolmogorov floor is not used.** `deflateRawSync()` byte length is not a mathematical Kolmogorov-complexity measure. Rejecting every password with fewer than nine compressed bytes would also reject legitimate inputs and would not prove that patterned strings are caught.
- **No generic SQL rewriting proxy is claimed.** Regex/token rewriting of arbitrary SQL cannot safely cover dialect grammar, comments, CTEs, nested queries, joins, aliases, procedures, views, prepared statements and dynamic SQL. The existing Prisma proxy remains the supported ORM scope guard; raw SQL is blocked there. PostgreSQL RLS must be applied and tested with real runtime roles.
- **No process-wide `fetch`/socket monkey-patch is installed.** Such patches can break host frameworks, DNS pinning, connection pools, native addons and runtime internals. Use explicit `arixSafeFetch` plus an OS-level egress firewall.
- **No home-grown Raft/quorum state server is claimed.** A correct consensus implementation requires durable logs, authenticated peer transport, membership changes, elections, term fencing, snapshot/install, recovery and fault-injection tests. Use the configured managed Redis service for shared production state until an independently reviewed consensus system exists.
- **No 5 ms CPU pre-emption promise is made.** Synchronous JavaScript cannot be interrupted by checking a deadline from inside the same event loop. A worker timeout can terminate a worker task but is not equivalent to a process or kernel sandbox.
- **No deployable gateway, customer firewall, mTLS origin policy, kernel egress rules, container/seccomp runtime, external KMS/HSM, independent WORM store, durable multi-region SOC, active-active replication, or signed SLSA attestation is implied by source-only additions.** Those controls require corresponding infrastructure and operational evidence.

## Verification boundary

The tests in this repository run locally with Node.js and, where relevant, the in-memory Redis preview adapter or injected test callbacks. They do not establish production multi-instance atomicity except for the Redis command contracts that are explicitly issued to the configured Upstash REST service. They do not establish ASVS certification, absence of vulnerabilities, universal false-positive/negative rates, volumetric DDoS resistance, or production RPO/RTO.
