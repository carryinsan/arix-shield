# Next.js multi-website integration

This guide connects one or more Next.js applications to a single deployed ArixShield control plane. Each application runs the WAF inside its own server-side request handler. The central ArixShield service supplies project policy, shared distributed quotas, reputation checks, abuse backoff, and sanitized outcome telemetry.

## 1. Install the server SDK

From each Next.js application repository:

```sh
npm install github:carryinsan/arix-shield#main
```

The package includes the SDK and its local server-side helper modules. Do **not** replace those imports with `https://arix-shield.vercel.app/schema.js` or `watermark.js`: the deployed ArixShield domain is an API endpoint, not a public JavaScript module CDN.

## 2. Configure server-only environment variables

Set these on the Next.js application's deployment:

```env
ARIXSHIELD_ENDPOINT=https://arix-shield.vercel.app
ARIX_SECRET_KEY=ARIX_SECRET_<your-project-server-key>
```

Use the exact server integration key generated by ArixShield. Never prefix it with `NEXT_PUBLIC_`, put it in client components, or return it in an API response. Keep the key in the server environment of each website. Use HTTPS for the control-plane endpoint.

## 3. Wrap App Router handlers

Example for `app/api/orders/route.ts`:

```ts
import { withArixShield } from 'arixshield/next';
import { auth } from '@/auth'; // Replace with your server-side session function.
import { waitUntil } from '@vercel/functions'; // Optional on Vercel.

export const runtime = 'nodejs';

const shieldOptions = {
  endpoint: process.env.ARIXSHIELD_ENDPOINT,
  serverKey: process.env.ARIX_SECRET_KEY,
  applicationId: 'storefront-production',
  mode: 'ENFORCE',
  globalRateLimit: true,
  getIdentity: async (_request: Request, { ip }: { ip: string }) => {
    const session = await auth();
    return session?.user?.id ? `user:${session.user.id}` : (ip ? `ip:${ip}` : 'anonymous');
  },
  waitUntil: (promise: Promise<unknown>) => waitUntil(promise),
  reportAllRequests: true
};

export const GET = withArixShield(async (_request: Request) => {
  // Keep your existing authentication, authorization, validation and data access here.
  return Response.json({ ok: true });
}, shieldOptions);

export const POST = withArixShield(async (request: Request) => {
  // Keep your existing handler logic here.
  const input = await request.json();
  return Response.json({ accepted: true, input });
}, shieldOptions);
```

Replace `auth` with the authentication library already used by your application. Do not read the user ID from a request header or request body. A client can forge those values. If the application has no login session, the example uses the trusted client IP as a fallback when available.

If the app is not hosted on Vercel, provide `getClientIp(request)` using the actual hosting provider's documented trusted-proxy mechanism. Do not blindly trust arbitrary `x-forwarded-for` or `x-real-ip` values from public requests. On Vercel, the SDK reads the platform-provided `x-real-ip`; when another proxy sits in front of Vercel, explicitly configure and validate the trusted proxy chain.

The optional `@vercel/functions` `waitUntil` integration lets outcome telemetry finish after the response. If you omit `waitUntil`, the wrapper awaits outcome reporting before returning whenever reporting is enabled. Install `@vercel/functions` in the Next.js app to use the Vercel example.

## 4. Connect multiple websites to the same ArixShield project

Use the same central endpoint in each application:

`https://arix-shield.vercel.app`

Give each application a unique stable `applicationId`, for example:

| Website | `applicationId` |
|---|---|
| Main website | `main-production` |
| Customer portal | `portal-production` |
| Admin dashboard | `admin-production` |

This value namespaces SDK actor identifiers and quota scopes. Without distinct IDs, identical users and route paths on different applications can share quota buckets. The ArixShield project policy remains centrally managed.

Where the ArixShield console supports multiple server integration keys, issue a separate server key per application and store each only in that application's server environment. Otherwise, a project server key can be shared server-to-server, with the unique `applicationId` providing application-level quota separation.

## 5. Keep the security boundary clear

- The WAF wrapper must execute before the route's business logic.
- Keep authentication, per-resource authorization, CSRF controls where applicable, input validation, and database ownership checks in the application. A WAF is not a replacement for them.
- The SDK's Node modules require the Next.js Node.js runtime; do not deploy these handlers using the Edge runtime.
- The browser SDK is optional telemetry and does not replace this server-side wrapper.
- Start with `mode: 'DRY_RUN'` on a staging deployment to inspect findings, then enable enforcement after reviewing real traffic. If you deliberately set `ENFORCE`, test login, checkout, uploads, and all legitimate high-volume routes.
- Keep endpoint and key configuration consistent across preview and production environments, and use distinct `applicationId` values for distinct deployments.

## 6. What this integration does not do

Pointing a website at the ArixShield domain alone does not protect that website. Every protected App Router handler must wrap its own route, and each deployment must have the correct server environment variables. Pages Router APIs need a corresponding Node adapter instead of this App Router example.
