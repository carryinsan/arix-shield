# Heavy-user, accessibility, and shared-network hardening

This document records the changes made to the six reported false-positive traps, how the ten-area architecture is actually implemented, and what remains intentionally unimplemented. It is not a promise of zero false positives or zero throttling.

## Six reported traps: implemented behavior

| Trap | Current behavior after this patch | Boundary / residual behavior |
|---|---|---|
| Sequential item IDs and dashboard fan-out | A verified HMAC capability in path, query, or JSON body is checked by the SDK and propagated to the outcome collector; a verified resource capability skips read-velocity counting. Successful `200` ID velocity is observation-only and never creates a BOLA ban. Denied `403/404` enumeration remains actor-scoped and can cause a short backoff. | Seals do not replace object-level authorization. Customer handlers still need tenant/owner predicates and must not expose an ID merely because it was sealed. Unsealed denied enumeration remains monitored. |
| Shared Wi-Fi / carrier NAT | Honeypot bans are keyed to a stable actor hash only. Raw IP is not a ban identity. IP/subnet/ASN/feed matches remain telemetry and correlation inputs; they cannot independently produce a block or challenge in `check-reputation`. Anonymous unverified actors are not merged by IP. | A stable identity is required to impose an actor ban. Subnet risk is an aggregate signal, not a reliable attribution to an individual. Account-level and broad aggregate quotas still exist. |
| Password, code, SQL tutorials, Markdown | Password/token/signature/clearance fields use type and byte caps and bypass generic SQL/comment/symbol heuristics. Free-text/rich-text fields bypass the SQL-comment grammar false positive but retain XSS, SSRF, traversal, command/prompt injection, parser, and structural checks. | Opaque-field recognition is name-based and capped; use the documented field names or configure the field profile. No text WAF can perfectly infer user intent. |
| Multi-tab / auto-save / infinite scroll | Verified DPoP users receive 2.5× quota; authenticated users with verified DPoP receive 4×. The four dimensions have independently sized actor, subnet, tenant, and route ceilings; server control-plane clamps now preserve those aggregate ceilings and the trusted multipliers. The browser wrapper smooth-paces only `GET`/`HEAD` when quota headers indicate near exhaustion. | Pacing is per browser tab and bounded (up to 300 ms). It does not replay writes or guarantee no `429`; a sustained rate beyond configured policy still receives a rate-limit response. No automatic PoW token lease top-up is enabled. |
| Brave, RDP/SwiftShader, keyboard and screen-reader use | Missing canvas/WebGL, software rendering, and zero pointer samples are neutral—not standalone bot verdicts. Keyboard dwell/focus transitions are recorded as optional interaction evidence. DPoP and prototype checks remain separate signals. | Interaction signals are heuristic and can be spoofed. Accessibility input is not required to receive clearance. This is not a claim that every assistive-technology combination has been usability-tested. |
| Wi-Fi / 5G / VPN handoff | Clearance validation no longer binds a session to IP prefix or JA4. DPoP thumbprint, signed claims, URL/method/body binding, nonce consumption, and replay checks preserve continuity across ordinary network changes. Geo-velocity is recorded as risk evidence, not a sole connection-kill rule. | IP changes do not bypass account authorization, request signatures, nonce replay protection, or quotas. DPoP key loss, browser storage clearing, expired clearance, or actual key compromise can still require re-verification. |

## Ten upgrade areas: implementation assessment

| Area | Implemented in repository | Honest status / required integration |
|---|---|---|
| 1. Authorization / AEE / BOPLA | Pre-handler route RBAC and tenant checks, mutation pre-check tripwire, read/write property filtering, structured `scopeQuery`, HMAC capability sealing for path/query/body, and optional response ownership guard. | SDK hooks are real, but `scopeQuery` cannot intercept arbitrary ORM calls, raw SQL, background workers, webhooks, or unwrapped admin code. Application route maps and actual database predicates are mandatory. |
| 2. Bot protection | Browser WebCrypto P-256 key, short-lived browser clearance, single-use clearance nonce, request-bound DPoP covering method/URL/body, and signed workflow breadcrumbs with replay protection. | Clearance is enforced only on configured/protected paths. Browser telemetry alone is not an identity guarantee. Dwell/focus data is advisory. |
| 3. Identity and keys | Per-email failed-login controls, TOTP, WebAuthn passkeys, server-key rotation with key epochs, and cache invalidation when a worker observes a new epoch. Login/signup request limits are account-scoped; network aggregate login envelope is broad to avoid NAT-wide 8/min throttling. | Worker caches are not globally revoked in 0 ms: remote policy snapshots can be cached for up to 30 seconds between control-plane fetches. No claim of instantaneous fleet-wide revocation. MFA/passkeys must be enrolled and enforced by the deployed account policy. |
| 4. WAF and parsers | NFKC normalization, duplicate JSON/query key checks, request-smuggling/header ambiguity checks, GraphQL depth/alias/introspection controls, MIME and upload magic-byte checks, XML DTD/XXE checks, OpenAPI validation, and safe-fetch URL/DNS/private-address checks. | OpenAPI/GraphQL/upload contracts require application schemas and correct middleware wiring. Parser heuristics and DNS/network controls need deployment tests against the actual runtime and egress network. |
| 5. Quotas and outages | Atomic multi-dimensional quotas, weighted requests/cost accounting, concurrency leases, local leases, circuit breakers, and restricted degraded-mode proof-of-work for low-risk reads. Mutations/auth remain fail-closed when their required security control is unavailable. | Exact behavior depends on Redis availability, configured tenant IDs, request cost weights, lease settings, and runtime topology. A quota is an explicit limit, not a guarantee of no throttling. No PoW-based quota bypass or automatic write replay is enabled. |
| 6. Security test lab | 2,500 deterministic attack mutations, 2,500 benign corpus samples, an 80-case actor/tenant/method/ID matrix, 100-way local/injected-adapter concurrency checks, 10 in-memory cron self-tests, and the 64-test unit/integration suite. | This is a deterministic regression corpus, not a 5,000-mutant coverage proof, exhaustive fuzzing, production traffic FP measurement, live Upstash load test, or external penetration test. |
| 7. Threat intelligence | Local IPv4/IPv6 prefix trie; Spamhaus DROP, FireHOL, Tor and optional AbuseIPDB feed parsing; weighted 0–100 risk telemetry; stale-feed decay; actor/subnet rolling correlation; verified crawler/provider checks. | The optional AbuseIPDB integration requires its key if enabled; it is not required by default. ASN list is a small contextual list, not comprehensive threat intelligence. JA4 is telemetry only and not a trusted identity. Shared-network reputation never independently hard-blocks. |
| 8. Audit and response | Redis-backed rolling HMAC event chain, Merkle audit anchoring, signed HTTPS webhook, dashboard IndexedDB witness, JSONL export, cron endpoint. | GitHub anchoring requires operator-supplied GitHub credentials and repository permissions. IndexedDB is trust-on-first-use, Redis is not WORM, and a master-secret/process compromise can forge evidence. Automatic containment is limited to configured supported transitions. |
| 9. Supply chain and runtime integrity | No package dependencies in `package.json`, deterministic SHA-256 manifest, syntax/import checks, selected lexical sink/secret checks, runtime API-library hash verification, production master-secret/private-JWK and HTTPS attestation. | The scanner is lexical, not a full AST SAST or dependency/SBOM scanner. The shipped manifest is unsigned because the production master secret is not packaged. Production release must sign it in trusted CI. Independent SAST/SCA/secret scanning and deployment attestation remain required. |
| 10. Deception | Schema-shaped decoy records with HMAC-derived identifiers, exposure registration, invisible-text/structural watermarking where possible, known reconnaissance-path recognition, and PHANTOM response behavior. | SDK honeypots only cover traffic passing through the SDK; they are not network-wide ghost routes or isolated sandboxes. Zero-width/key-order watermarks can be stripped. Decoys are not guaranteed semantically indistinguishable from customer data. |

## Why some proposed Plan B shortcuts were not enabled

- No invisible canary URL was injected into ordinary response metadata. A client-visible secret link can be discovered by scripts, but its secrecy is not a strong security boundary, and automatically banning on retrieval would risk false positives from previewers, link scanners, prefetchers, and accessibility tooling. Registered, schema-shaped canary records remain an opt-in deception signal.
- No 15 ms/25 ms proof-of-work token top-up bypasses quota. It would let the client mint extra write budget and could cause automatic replay of non-idempotent requests. Rate limits remain enforceable; safe read pacing is the only automatic client smoothing.
- No 30-day localStorage/cookie loyalty bearer bypass was introduced. A persistent browser-readable bearer can be copied/replayed and complicates revocation. The current model uses a non-exportable IndexedDB key and short-lived, single-use, request-bound proofs.
- No claim is made that an attacker is blocked in `<0.1 ms`, that a normal user sees exactly `0 ms` impact, or that 100% of attacks are blocked. Redis, network, browser crypto, and customer handler latency are real costs.

## Local verification and release boundary

Run `npm test`, `npm run check`, and `npm run audit:verify` from this repository. In this workspace, Upstash is not configured; tests use the ephemeral in-memory Redis adapter, which explicitly does not share state between serverless instances and loses data on restart. Before production, configure the existing Upstash values and `ARIX_MASTER_SECRET`, generate the clearance RSA key pair, sign the integrity manifest in trusted CI, validate cron jobs, and run integration/load/chaos tests against the deployed stack.

OWASP ASVS 5.0.0 is the stable release published by OWASP on 30 May 2025. This repository has not been independently mapped and assessed requirement-by-requirement at Level 3. The present archive is therefore a hardened implementation with local regression evidence, **not an ASVS Level 3 certification or a claim of zero vulnerabilities**.
